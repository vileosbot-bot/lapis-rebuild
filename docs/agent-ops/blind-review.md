# 子代理盲审协议

- request-id：agent-7x24-p01-gate-20261116-01

## 1. 盲审输入

子代理只能收到以下三类材料：
1. 本次 PR 的代码差别（PR diff；不扩展到无关历史代码）。
2. 机器门禁结果，包括各项 PASS/FAIL/UNKNOWN、日志定位和改动清单。
3. 任务原始简报（用户最初派活内容，不附带总管的中间裁决）。

总管应提供原始简报和必要上下文，但不得提供：
- 总管此前的审查结论、倾向或风险判断；
- 工人对自身实现的解释、辩护或“已自检通过”陈述；
- 其他审查者的评论或 verdict；
- 暗示希望通过/拒绝的引导语。

若 GitHub PR 页面已包含工人解释，盲审材料应只抽取 diff、门禁结果和原始简报，不把解释转发给子代理。

## 2. 子代理任务

子代理应独立阅读材料，重点检查需求覆盖、回归风险、权限/数据安全、失败处理、测试充分性和文档一致性。不得因为机器门禁 PASS 就默认代码正确。

输出按严重程度从高到低排列的问题清单。每个问题必须包含：
- 严重程度：阻断 / 高 / 中 / 低；
- 文件路径和具体行号（无法精确定位时说明原因）；
- 事实依据及可能后果；
- 建议修复或需要补充的证据。

最后必须给出：
- 是否建议通过：建议通过 / 有条件通过 / 不建议通过；
- 尚未解决的问题；
- 本次实际审查的 PR head SHA；
- 说明没有读取哪些被排除材料。

无问题也要明确写“未发现阻断问题”，不能只给一句“LGTM”。

## 3. 各等级要求

- 绿灯：子代理盲审必须完成；总管每 5 个抽 1 个复核。未完成子代理盲审，不得写“已审查通过”。
- 黄灯：子代理盲审后，总管逐项验收。
- 红灯：必须由 Opus 执行盲审，再由总管最终裁决。子代理或同一模型重复阅读不能代替 Opus。

## 4. 独立性短板（必须公开）

当前子代理与总管使用同一模型、同一台电脑，只能串行进行第二遍阅读。即使输入材料隔离，也不等于不同模型、不同执行环境或真正独立组织的审查视角；可能共享模型偏差、上下文污染和推理盲点。

因此：
- 绿/黄灯子代理盲审是第二遍串行检查，不得宣传为 Opus 级独立复核。
- 红灯必须单独取得 Opus 盲审证据。
- 总管不得把自己的复核包装成子代理盲审，也不得把子代理结论包装成 Opus verdict。
