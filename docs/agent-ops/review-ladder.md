# Agent Ops 审查阶梯

- request-id：agent-7x24-p01-gate-20261116-01
- 适用范围：vileosbot-bot/lapis-rebuild 的 PR。
- 试运行方式：参考模式；机器结果用于提示与记录，不启用 required-check 分支保护，不自动合并。

## 1. 分级规则

### 绿灯：小修

同时满足：
- 只改文案、样式、注释或非核心小逻辑；
- 初始阈值为 diff 增删合计不超过 50 行；
- 不触及红灯清单；
- 机器门禁八项全部 PASS。

流程：门禁通过 → 子代理盲审 → 总管抽查（每 5 个绿灯 PR 抽 1 个）。子代理盲审未完成或未通过，不得标记“已审查通过”。被抽中的 PR 必须等待总管抽查结论。

### 黄灯：中改

包括超出绿灯阈值、一般功能逻辑、跨模块调整，或自动分级无法可靠判断的变更。

流程：门禁通过 → 子代理盲审 → 总管逐项验收。缺少任一环节，不得标记审查通过。

### 红灯：高风险

触及以下任一类即红灯：
- 钱：余额、价格、资产、计费、财务或交易；
- 删除：删除文件、数据、不可恢复内容；
- 上线：部署、发布、生产环境切换；
- 冻结：模型/规则/数据冻结、基准锁定；
- 支付：支付流程、支付凭证；
- 权限：账号权限、仓库权限、令牌权限、Actions 写权限、访问控制。

流程：门禁通过 → Opus 盲审 → 总管最终决定。没有 Opus 盲审证据，不得合并；总管拥有最终决定权。机器分类只能提出等级，无法判断语义时按更高一级处理。

## 2. 分级与状态纪律

- FAIL 或 UNKNOWN 的 PR 不进入审查通过状态。
- 分级有争议，一律先按高一级执行。
- 绿灯的“总管每 5 个抽 1 个”是抽样验收，不免除子代理盲审。
- 黄灯必须总管逐项验；红灯必须 Opus 盲审且总管最终决定。
- 机器脚本以文件路径和 diff 变更行关键词提示红灯，包括钱/资产、删除、部署/发布、冻结、支付、权限/认证；.github/workflows/** 或 tools/gate/** 自身变更也强制红灯，并在评论标注“本 PR 修改了门禁自身，结果不可信”。这是保守启发式，可能误判或漏判，不替代人工语义审查。权限文件变更、删除和上线相关变更优先按红灯。
- 本轮任务修改 GitHub Actions 权限（synthetic gate job 增加 PR 读写与 issue comment 写权限；private-original 仍只读），因此预期被判为红灯；不能由本任务执行者自行代替 Opus 审查。

机器脚本中的 review_decision() 目前仅是函数级策略判断，未接入 workflow，也不会生成 BLOCKED 状态；实际审查流程仍由负责人依据本阶梯人工执行。

## 3. 试运行边界

本机制先按参考模式运行并记录误判、漏判、耗时和复核差异。当前没有启用 branch protection/ruleset required status checks，不能声称 GitHub 已在技术上阻止所有违规合并。操作纪律仍是：红灯缺 Opus 或总管裁决时不得合并；绿灯缺盲审时不得标记审查通过。升级为硬前置必须由负责人另行明确批准。

## 4. 审查台账

每个已合并 PR 必须且只能对应一条审查台账记录。历史 PR 只建立事实基线行，明确标注“门禁启用前历史记录，不追认本阶梯审查”；不得伪造历史盲审或 Opus 结论。试运行开始后的 PR，在其合并后补入真实门禁结果、分级、盲审者、总管结论和合并 SHA。

台账文件：docs/agent-ops/review-ledger.md。机器读回比较 PR 编号集合，不只比较行数，避免同一 PR 重复或遗漏。
